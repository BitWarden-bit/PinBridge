PinBridge — 架构设计

给 Windows 程序做动态分析（脱壳 / 逆向 / 对抗 VMP 混淆）的工具台：底层把 Intel Pin 的能力翻译成谁都能调用的 C 接口，中间是一个住进目标进程的调试代理，上面用 Python 插件写分析逻辑；逐指令的重活靠「先录下来，再离线慢慢拆」。

调试代理
调试代理 pinbridge_agent.dll —— 整套系统的 runtime 核心 一个被 Pin 加载进目标进程的 DLL（PinTool）。你在进程外下的每条命令、注入的每个 Python 插件，最终都是它在目标进程内部执行。 Rust 编写 · 三条工作线程
查询服务线程
接令办事的窗口：前端每条命令（停/走/读内存/下断点…）都是一次短连接，它执行完立刻回结果。没客户端时纯睡觉，零开销。query_server.rs
脚本线程（内嵌 Python 3.10）
你的 .py 插件随时注入、随时卸载 —— 哪怕目标正停在断点上。插件声明「我关心什么事件」，事件来了它回调你的函数。scripting/ · 解释器编进代理，无外部依赖
录制线程
trace 录制专用：先把事件存进一块大内存（默认 100 万条），再慢慢写成文件，不拖慢目标。record.rs → .pbtr
运行时核心（在目标指令被执行的瞬间工作）
事件环形缓冲
一块 64K 格的循环存储：目标产生的每个事件（执行了哪条指令、碰了哪个内存…）占一格，写满就覆盖最旧的，像循环录像带。格子定长、写入时不分配内存，所以撑得住每秒上千万条。ring.rs
调试 & 观测引擎
断点（64 个，命中即精确停住）、hook 点（4096 个，专门抓函数前四个参数 —— 「hook 全部 ntdll 导出」就靠它）、单步、syscall 监控、异常监控。bp.rs · hooks.rs · stepper.rs · syscall_engine.rs
代理通过 689 个纯 C 函数调用 Pin —— 调用约定 __cdecl
C 接口桥
pinbridge.dll —— 把 Pin 翻译成通用 C 接口的桥 Pin 本身是 C++ 的，别的语言没法直接调用。这个 DLL 把 Pin 的能力逐个包装成 689 个纯 C 函数（pb_* 开头），版本冻结（v1.5）：接口一旦发布就永不变更，任何语言（Rust/C/Python/Go…）都能通过它写 PinTool。 C++ 编写 · 只暴露 C
导出面
689 个 pb_* 函数，外加常量、结构体、回调类型定义ABI v1.5 冻结
三层实现
每个功能分三层：对外门面 → 抽象接口 → 真正的 Pin 调用。好处：测试时可以把「真正的 Pin」换成假的（mock），不开 Pin 也能跑 60 项契约测试。facade → backend → Pin 实现
六种预制采集器
C 接口不支持可变参数，Pin 的「任意组合采集」没法直接暴露。所以预做了 6 种最常用组合：抓四个参数寄存器 / 记每次内存访问 / 记每条指令执行 / 记分支去向 / 记指令字节 / 记内存读写的值。capture_regs · memory_operands · exec · branch_edge · exec_bytes · memory_operands_values
隔离纪律（为什么稳）
桥两边互不分配对方的内存；要字符串就「你给缓冲区、它告诉你需要多大」；句柄不透明。因此桥和使用方的 C 运行库完全隔开，不存在跨 DLL 释放内存导致的崩溃。opaque handle · 三段式缓冲区 · CRT 隔离
桥内部调用的才是 Pin 的 C++ API
Pin
Intel Pin 3.31 —— 指令插桩引擎（进程的真正宿主） 它在目标程序运行时把机器码即时重编译（JIT），并按我们的要求在某些指令前后安插回调（「执行到这里就记一笔」）。代理 DLL 和桥 DLL 都是以「工具插件」身份被它用私有方式加载的。 启动：pin.exe -t pinbridge_agent.dll -- 目标.exe
回调跑在目标自己的线程上 —— 所以代理内部的纪律极严（见下方数据流 A 的警告）
目标
目标进程 —— 被分析的 Windows 程序 VMP 壳样本、要脱壳的程序、或任意 exe
三条数据流（系统里真正在跑的三条路）

A 事件高速通道

每秒可达千万级 —— 目标跑指令时事件怎么流出来
1Pin 重编译目标代码时，按我们的要求安插「记录点」
2只在你关心的地址范围内安插（范围过滤），范围外零成本
3目标执行到记录点，预制采集器抓取现场：寄存器 / 内存地址 / 分支去向 / 指令字节
4现场打包成定长小记录，写进环形缓冲 —— 不分配内存、不做 I/O、永不等锁
5谁想看谁自己翻页：查询服务、脚本线程、录制线程都是被动读者，写事件永远不等任何人
!这条路上禁用标准库锁和内存分配（实测会高概率搞死进程）—— 只允许用 Pin 自己的锁

B 命令通道

低频 —— 你下的每条命令怎么走
1你（前端 / 脚本 / AI）发命令：停、走、读内存、下断点、改寄存器…
2命令经客户端库 → 本机回环协议 → 查询服务线程执行
3断点命中时目标精确停住（停在断点指令执行之前），你看完现场再让它继续
4单步 si/so：靠「让线程停在回调里等信号」实现，落点精确；so 遇 CALL 自动放一次性断点
5观测命令：模块 / 线程 / 导出枚举、符号解析、反汇编、引擎开关、syscall 号码过滤
!「停止」和「继续」必须由同一条专用线程执行（Pin 的配对限制），换线程执行会直接崩

C 脚本 & 录制 / 离线分析

污点分析主链 —— 先录后拆
1Python 插件声明关心的事件；脚本线程每 ~5ms 收一批送进你的回调
2插件里每个动作（读内存、下断点…）= 一次进程内回环调用，微秒级
3要逐指令分析时：pb.trace_start() 圈定地址范围开始录制
4录制线程把事件写成 .pbtr 文件（每条指令的字节 + 每次内存访问的地址和值）
5离线用 taint.py 慢慢拆：前向污点（这数据流向哪）+ 反向切片（这值谁算出来的）
!录制里有每次内存访问的具体地址，所以「谁写了这个地址」一查便知，不需要静态分析里最头疼的别名推断；代价是录制必须无损 —— 丢了事件，这个窗口就得重录
污点分析三层路线图
① 编排层 · 已完成
Python 插件系统：事件来了自动回调你的函数；插件里可以下断点、读写内存、改寄存器、停走单步、查符号。换分析思路不用重新编译 —— 改 .py 文本随时注入。pb_init / on_event_batch / on_bp_hit / bp_set / hook_set / read_mem…
② 录制通道 · 已完成（ABI v1.5）
把目标「跑过的那段窗口」原样录下来：每条指令的字节、每次内存访问的地址和值，写满 100 万条的内存缓冲后由后台线程落盘。命令：trace start / trace stop，产物 .pbtr。
③ 离线分析层 · 原型已验证
纯 Python 离线库（examples/python/replay/）：capstone 解码、字节级影子内存、前向污点传播 + 反向切片。已对测试程序切出精确切片；16 个单元测试。
一句话总结：Pin 负责「在目标代码里安插记录点」；pinbridge.dll 负责「把 Pin 翻译成谁都能调用的 C 接口」； 调试代理负责「住在目标进程里干活」——抓事件、管断点、跑 Python 插件、录 trace；协议和前端负责「把数据和按钮递到你手上」； 真正的分析逻辑（污点、反混淆、脱壳策略）永远是 .py 文本，不用编译，随时注入。
各层互不分配对方内存接口冻结永不变事件每秒千万级 vs 界面每秒 60 帧界面卡死不影响采集先录后拆：重活全在离线 Python

# 框架设计 · 架构图配文（接在「架构如下：[图]」之后）

ABI : 主要是把Pin的Cpp 转成C方便给其他语言再次开发。C++的类、异常、STL这些东西是没法直接跨语言边界的，所以全部冻结成纯C函数——689个`pb_*`导出，ABI v1.5，定死不动了。顺带解决了一个隐藏坑：两边的CRT完全隔离，Pin那边用的是它自己的PinCRT，我消费方DLL用什么CRT编译都跟它不打架。

Agent : 整个平台的核心，Rust写的cdylib（pinbridge-agent.dll），被Pin私有映射进目标进程里跑。主要干三件事：

1. 插桩抓事件，写进一个64K定长槽的ring。热路径上零分配、零IO、不panic，实测全范围插桩1360万事件大概1.5秒，性能是够用的。
2. 三个旁路线程：查询线程（被动响应外面的命令，没客户端连着就是零成本）、脚本线程（内嵌了CPython，插件随时热加载，应付突发情况就靠它）、录制线程（把跑过的执行流无损落盘成.pbtr，后面做污点分析用）。
3. 断点、单步、syscall引擎这些传统调试器能力，全部在Pin这一层自建，不走Windows的调试API。需求9、10（接管异常、自建调试）的落点就在这里。

proto/client : 对外的二进制查询协议（loopback TCP）加统一的客户端封装。前端也好、脚本也好、后面要接的MCP也好，都走同一个口子，协议是唯一契约。前端同时还兼职启动器——一条命令把pin+agent+目标拉起来，退出的时候自动回收进程树。

前端 : cli/tui/ui三个壳而已。原则是headless一等公民——所有功能先在CLI里无界面验证通过，UI只是之后的美化层。前端断线重连后端照跑，互不影响。
